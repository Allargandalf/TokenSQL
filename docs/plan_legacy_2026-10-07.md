# TokenSQL：本地大模型驱动的 Token 报价数据库

## 项目目标

开发一个基于本地 Qwen-32B 的 Token 报价管理系统。

系统需要支持来自不同供应商、格式不统一的 Excel 报价文件，通过本地 Qwen 完成语义解析、模型名称标准化和计费信息提取，并将结果存储到关系型数据库。

同一个模型需要支持多个 Token 供应商，每个供应商可以针对同一模型提供多个报价方案。系统还需要独立维护模型官方价格，支持自动获取、历史更新和报价比较。

## 执行要求

### 第一阶段：环境调查

首先检查服务器的真实目录结构、项目目录状态、Python 环境、现有数据库服务及 GPU 资源。

重点检查已经部署的 Qwen-32B，包括具体模型版本、推理框架、API 访问方式、结构化输出能力及 Function Calling 支持情况。

测试服务器是否具有外部互联网访问权限，尤其是访问模型厂商官方 API 文档和定价页面的能力。

不得随意停止、重启或修改现有 Qwen 服务，也不得影响其他用户的进程。

环境调查完成后，输出实际检查结果及推荐技术方案。

### 第二阶段：数据库设计

优先评估 PostgreSQL + SQLAlchemy，必要时允许使用 SQLite 构建初步原型。

设计模型厂商、标准模型、模型别名、Token 供应商、报价方案、价格记录、数据来源和 Excel 导入记录。

满足以下要求：

* 一个模型对应多个 Token 供应商。
* 同一个供应商可以提供多个报价方案。
* 每个报价方案包含多个计费维度。
* 独立管理模型标准名称、实际版本和 API 别名。
* 支持官方价格、第三方报价及报价历史。
* 保留原始价格、原始货币、原始单位及标准化结果。
* 保留数据来源、更新时间及验证状态。

先完成数据库关系设计和迁移脚本，再开发数据导入功能。

### 第三阶段：智能 Excel 解析

实际读取提供的 Excel 样表，分析 Sheet、表头、合并单元格和报价格式。

优先通过 Python 提取明确的结构化信息，通过本地 Qwen 完成存在歧义的语义解析。

使用严格的结构化输出与校验机制。

模型匹配按照精确匹配、模糊匹配及 Qwen 语义判断的顺序执行。

禁止 Qwen 直接决定数据库主键或执行 SQL。

对于无法确定的模型、版本、币种及价格，创建待审核记录，不允许直接猜测或自动覆盖已有数据。

人工确认结果应保存为后续可复用的模型别名或解析规则。

### 第四阶段：官方价格采集

开发与 Excel 导入相互独立的官方价格采集模块。

优先使用官方定价文档及官方 API。

检查本地 Qwen 是否能够通过现有部署方式调用外部工具。如有必要且获得授权，可通过 Python HTTP 工具或 Qwen-Agent 提供网络获取功能。

Qwen 主要负责从官方网页中提取和解释价格，实际联网、校验及数据库更新由 Python 执行。

优先为缺失官方价格的模型补充报价，并提供独立的定时更新功能。

保存每次抓取的来源、时间、原始数据、适用条件及验证状态。

不得使用无来源的搜索摘要直接生成官方价格。

### 第五阶段：价格标准化

默认使用人民币/百万 Token 作为可比较的标准价格，同时保留原始报价。

支持不同货币、Token 单位、输入输出价格、缓存价格、峰谷价格和其他特殊计费条件。

跨币种换算需要保留汇率及其来源日期。

只有计费维度相同的价格才允许进行直接比较。

### 第六阶段：管理界面及测试

使用 FastAPI 提供数据接口，并评估 Streamlit 作为第一版管理界面。

支持 Excel 导入、模型别名管理、异常审核、报价查询、供应商比较和数据导出。

建立自动化测试，特别关注错误模型合并、重复导入、价格单位转换、模型版本变化及官方价格更新等问题。

使用真实样表完成端到端测试。

## 开发约束

1. 不覆盖或删除服务器已有文件。
2. 不修改正在运行的 Qwen 服务，除非明确获得授权。
3. 所有数据库结构和代码应模块化，便于后续增加供应商和模型。
4. 不允许 Qwen 未经校验直接写入生产数据库。
5. 原始数据和历史价格必须可追溯。
6. 对不确定的数据，应明确标记并提交人工审核。
7. 优先完成稳定、可验证的基础版本，不必在第一版开发复杂前端。

## 预期交付

提供完整可运行的项目代码、数据库结构、Excel 解析模块、本地 Qwen 调用模块、官方价格获取模块、管理界面、测试用例和部署文档。

首先完成服务器与 Qwen 环境调查，以及数据库设计。根据实际情况确定技术实现后，再继续开发其余模块。
